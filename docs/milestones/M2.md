# Milestone 2: Make a Song

Status: **draft for owner review** (2026-10-11). It implements DESIGN.md as decided (§1 milestone M2 and the sections it touches) plus the owner's 2026-10-11 audio wishes. Nothing starts until the owner approves it.

## Goal

A person in the UI, or an agent through MCP alone, can make a **full song**:
- arrange sections with automation (filter sweeps, volume rides);
- use **audio**: drop a loop that follows the project tempo, record a vocal or instrument, edit it, chop it;
- play **third-party CLAP and VST3 plugins** next to the built-ins, controlled from a MIDI keyboard;
- bring in an existing **FL Studio project** to keep working on it.

## Acceptance criteria

M2 is done when all of these hold on `main` with CI green on Windows, Linux and macOS:

1. **Agent acceptance test (MCP only).** A scripted agent builds a 32-bar song:
   - intro / build / drop sections;
   - a filter sweep and a volume automation clip;
   - a drum loop imported as audio and fitted to the project tempo;
   - a slice-instrument made from that loop;
   - one plugin instance (the repo's own test CLAP plugin);
   - at least two M2 effects (e.g. multiband compressor and convolution reverb).

   The export matches the offline oracle, sits between -14 and -8 LUFS, and doesn't clip. The analysis reports the section structure.
2. **By hand (owner).** Record audio from your interface, edit it in the audio editor (trim, fade, normalise), slice a loop, draw automation, play one of your own VST3 plugins from a MIDI keyboard with MIDI learn on a knob, and export. No dropouts at 256 samples.
3. **FLP import.** Over your local FL 21 project corpus (never committed), the import report lists every project as opened, with its counts of channels, patterns, notes, playlist clips, mixer routes and automation. At least 90% of the notes and clips come over correctly, checked by an automated diff against an independent reading of each file. Everything approximated or skipped is listed.
4. **Plugin robustness.**
   - A plugin scan of your installed plugins completes, producing a compatibility report.
   - A deliberately crashing test plugin is caught, the session keeps running, and the plugin is marked *isolate* (DESIGN §6; full out-of-process isolation stays M4).
   - Plugin state survives save and reopen.
5. **Stretch quality.** Fit-to-tempo across ±30% stays within agreed objective bounds (pitch drift, transient smearing, measured on generated material). The owner signs off by listening.
6. **The oracle and real-time safety, extended.** Audio clips, automation and recording-monitor paths keep live output bit-identical to the offline render, and keep allocation off the audio thread. Third-party plugins are exempt from bit-exactness, but the test plugin is not.
7. **Performance.** The reference project plus 8 stretched audio clips plus 4 automation clips stays within 25% DSP load on the reference machine, and disk streaming never underruns.
8. **Coverage and parity.** Every new command has schema and behaviour tests. Every M2 row of `docs/parity/fl-studio.md` has both columns filled.

## Scope

### Audio clips and tempo (the owner's audio wishes)

- **Audio clips in the playlist:** drag in from Explorer (building on T9) or the browser; trim either edge; slip-edit; split.
- **Clip settings:**
  - fade-in and fade-out handles with curve shapes;
  - gain, reverse, and pitch in semitones and cents;
  - waveforms drawn and cached per zoom level.
- **Per-sample BPM:** detected automatically by onset and tempo analysis (extending `ph-analysis`), and editable.
- **Stretch modes per clip:** *Resample* (turntable), *Stretch* (keep pitch, follow tempo) and *Slice* (re-time at transients). **Fit to tempo** in one click; tempo-synced clips follow tempo changes.
- **Stretch engine:** Signalsmith Stretch (MIT). Rubber Band is GPL and must not be used. Confirm the Rust binding's licence in the contracts phase, or write a thin binding of our own.
- **Warp markers** (Ableton-style, beats pinned in the audio): **owner decision**, either a stretch goal in M2 or postponed.

### Audio editor and slicer

- **Edison-style editor:** record, select, cut, copy, paste, trim, normalise, fade in and out, reverse, silence, gain, and a simple de-click.
- **Never overwrites:** edits write a new file in `samples/`, so the original is never overwritten and undo works (DESIGN: never delete user data).
- **Slicer:** detect transients (with a sensitivity setting), adjust slice markers by hand, and build a sliced Sampler instrument, one slice per key, with an option to write a pattern that replays the original loop.

### Recording

Audio input via cpal: arm a track or channel, monitor with a latency readout, record count-in and punch, and save takes into `samples/` as audio clips. The design also asks for WASAPI exclusive mode where cpal lacks it, which is a T3 follow-up.

### Automation

- **Automation clips in the playlist:** points with curve types (linear, hold, smooth, S-curve) on any automatable parameter (instrument, effect, mixer, tempo).
- **Creating them:** "Create automation clip" from a knob's right-click menu (T8 left a placeholder for this).
- **Recording automation** from knob movement while playing.
- **Engine:** sample-accurate automation, plus tempo automation through the `TempoMap`.

### MIDI controllers

- MIDI input via midir.
- Note input to the selected channel, with record-to-pattern.
- **MIDI learn** for any knob (T8 placeholder). Controller mappings are saved per user.
- **`ph-node` gains CC, pitch-bend and per-note expression events** (the T2 contract gap). The Haus Synth's mod-wheel and bend become real events.

### Plugin hosting (DESIGN §6)

- **Formats:** CLAP and VST3 instruments and effects, in-process.
- **Scanner:** with a cache and a blocklist.
- **Plugin windows:** embedded in our floating plugin windows where the OS allows it, otherwise floating. A generic parameter UI is always available, and agents can drive any plugin by parameter id.
- **State:** saved with the project as separate files (DESIGN §10).
- **Crash handling:** a crash in a plugin call is caught as far as the platform allows, the node goes silent, and the plugin is marked *isolate* (out-of-process isolation itself is M4).
- **Test plugins:** the repo builds its own test plugins (a simple synth, a gain and a crash-on-demand plugin) so CI never depends on third-party plugins. Your own installed plugins are scanned locally to produce the compatibility report.

### Effects suite, M2 part (DESIGN §7)

Multiband compressor, gate/expander, convolution reverb (with a few generated impulse responses), chorus, flanger, phaser, bitcrush, stereo tools, and spectrum, loudness and phase analysers (as effect windows).

### FLP import (moved into M2 at the owner's request)

**Clean-room, as two separate roles.** PyFLP, the best-known reference, is GPL code, so no PyFLP code is read or translated.
- A **spec agent** writes `docs/formats/flp.md` as plain facts (event ids, structures, meanings) from public documentation and from inspecting the owner's own FL 21 files. It cites its sources.
- A **different implementer agent** builds the importer from that spec only.

**What it imports:** channels, patterns and notes, playlist (pattern clips, audio clips, automation clips), mixer routing and levels, and tempo. Third-party plugin states carry over. Native FL plugins map to the closest Patternhaus equivalent or become labelled placeholders that keep their data. An import report is written.

**Testing:** fuzz the parser. Your FL projects are the local test corpus only.

### Agent abilities, M2 (DESIGN §5)

- **Rendered audio clips** returned to audio-capable models.
- **Reference-track comparison:** tonal balance, loudness and stereo width against a reference you supply.
- **Agent preview mode** (deferred from M1): an agent's batch shows as ghost notes and clips you accept or reject.
- Agent tools for audio clips, automation, plugins and the editor are all commands, as always.

## Contracts fixed in T0 (draft)

1. **`ph-core`:**
   - `Clip` gains a kind, either `Pattern` or `Audio { sample, offset, gain, fades, pitch, reverse, stretch: Resample | Stretch | Slice, bpm }`;
   - `AutomationClip { target: ParamPath, points: [{tick, value, curve}] }`;
   - a project `samples` registry (reference → metadata: BPM, length, channels, detected key and onsets, provenance);
   - recording takes.

   All additive with serde defaults. `format_version` becomes 2, with a migration test from 1.
2. **`ph-node`:**
   - `EventKind::{Cc, PitchBend, NoteExpression}`;
   - `Processor::load_state` receives an `&dyn AssetResolver`;
   - the parameter-automation contract (sample-accurate value or ramp events).
3. **Plugin node API (`ph-plugin-host`):** adapts CLAP/VST3 instances to `Processor`, with scan results, state blobs, editor-window handles and the crash-catch boundary.
4. **`ph-engine`:** a streaming audio-clip node, an automation evaluator and an input/recording API. `render_offline` gains the input-free path.
5. **Commands:** new families `audio.*`, `automation.*`, `plugin.*`, `record.*`, `midi.*`, `slicer.*`, `editor.*` and `file.import_flp`.

## Risks

| Risk | Mitigation |
|---|---|
| Plugin hosting is the hardest track: GUI embedding in egui windows, VST3 quirks, crashes | Test plugins in the repo; CLAP first; generic parameter UI as the fallback; your plugin report decides what "supported" means |
| FLP clean-room discipline | Two agents, the spec in its own track, the implementer never sees PyFLP, sources cited in the spec |
| Stretch quality and licensing | Signalsmith (MIT) plus objective tests and your listening sign-off; licences confirmed in T0 |
| Real-time safety with disk streaming and plugins | Streaming prefetch off the audio thread, tested under `assert_no_alloc`; plugins are outside our control, so they're measured, not trusted |
| Cloud VMs: 4 vCPU, 16 GB, pause when idle | Assign only build-and-test tracks to the cloud; long fuzzing and perf stay local |
| The cloud credit expires around Nov 4–5 | Phase B starts as soon as T0 lands; cloud tracks are front-loaded |
