## Goal

A person in the UI, or an agent through MCP alone, can make a **full song**:
- arrange sections with automation (filter sweeps, volume rides);
- use **audio**: drop a loop that follows the project tempo, record a vocal or instrument, edit it, chop it;
- play **third-party CLAP and VST3 plugins** next to the built-ins, controlled from a MIDI keyboard;
- bring in an existing **FL Studio project** to keep working on it.

## Acceptance criteria

M2 is done when all of these hold on `main` with CI green on Windows, Linux and macOS:

1. **Agent acceptance test (MCP only).** A scripted agent builds a 32-bar song:
   - intro / build / drop sections;
   - a filter sweep and a volume automation clip;
   - a drum loop imported as audio and fitted to the project tempo;
   - a slice-instrument made from that loop;
   - one plugin instance (the repo's own test CLAP plugin);
   - at least two M2 effects (e.g. multiband compressor and convolution reverb).

   The export matches the offline oracle, sits between -14 and -8 LUFS, and doesn't clip. The analysis reports the section structure.
2. **By hand (owner).** Record audio from your interface, edit it in the audio editor (trim, fade, normalise), slice a loop, draw automation, play one of your own VST3 plugins from a MIDI keyboard with MIDI learn on a knob, and export. No dropouts at 256 samples.
3. **FLP import.** Over your local FL 21 project corpus (never committed), the import report lists every project as opened, with its counts of channels, patterns, notes, playlist clips, mixer routes and automation. At least 90% of the notes and clips come over correctly, checked by an automated diff against an independent reading of each file. Everything approximated or skipped is listed.
4. **Plugin robustness.**
   - A plugin scan of your installed plugins completes, producing a compatibility report.
   - A deliberately crashing test plugin is caught, the session keeps running, and the plugin is marked *isolate* (DESIGN §6; full out-of-process isolation stays M4).
   - Plugin state survives save and reopen.
5. **Stretch quality.** Fit-to-tempo across ±30% stays within agreed objective bounds (pitch drift, transient smearing, measured on generated material). The owner signs off by listening.
6. **The oracle and real-time safety, extended.** Audio clips, automation and recording-monitor paths keep live output bit-identical to the offline render, and keep allocation off the audio thread. Third-party plugins are exempt from bit-exactness, but the test plugin is not.
7. **Performance.** The reference project plus 8 stretched audio clips plus 4 automation clips stays within 25% DSP load on the reference machine, and disk streaming never underruns.
8. **Coverage and parity.** Every new command has schema and behaviour tests. Every M2 row of `docs/parity/fl-studio.md` has both columns filled.

## Scope

### Audio clips and tempo (the owner's audio wishes)

- **Audio clips in the playlist:** drag in from Explorer (building on T9) or the browser; trim either edge; slip-edit; split.
- **Clip settings:**
  - fade-in and fade-out handles with curve shapes;
  - gain, reverse, and pitch in semitones and cents;
  - waveforms drawn and cached per zoom level.
- **Per-sample BPM:** detected automatically by onset and tempo analysis (extending `ph-analysis`), and editable.
- **Stretch modes per clip:** *Resample* (turntable), *Stretch* (keep pitch, follow tempo) and *Slice* (re-time at transients). **Fit to tempo** in one click; tempo-synced clips follow tempo changes.
- **Stretch engine:** Signalsmith Stretch (MIT). Rubber Band is GPL and must not be used. Confirm the Rust binding's licence in the contracts phase, or write a thin binding of our own.
- **Warp markers** (Ableton-style, beats pinned in the audio): **owner decision**, either a stretch goal in M2 or postponed.

### Audio editor and slicer

- **Edison-style editor:** record, select, cut, copy, paste, trim, normalise, fade in and out, reverse, silence, gain, and a simple de-click.
- **Never overwrites:** edits write a new file in `samples/`, so the original is never overwritten and undo works (DESIGN: never delete user data).
- **Slicer:** detect transients (with a sensitivity setting), adjust slice markers by hand, and build a sliced Sampler instrument, one slice per key, with an option to write a pattern that replays the original loop.

### Recording

Audio input via cpal: arm a track or channel, monitor with a latency readout, record count-in and punch, and save takes into `samples/` as audio clips. The design also asks for WASAPI exclusive mode where cpal lacks it, which is a T3 follow-up.

### Automation

- **Automation clips in the playlist:** points with curve types (linear, hold, smooth, S-curve) on any automatable parameter (instrument, effect, mixer, tempo).
- **Creating them:** "Create automation clip" from a knob's right-click menu (T8 left a placeholder for this).
- **Recording automation** from knob movement while playing.
- **Engine:** sample-accurate automation, plus tempo automation through the `TempoMap`.

### MIDI controllers

- MIDI input via midir.
- Note input to the selected channel, with record-to-pattern.
- **MIDI learn** for any knob (T8 placeholder). Controller mappings are saved per user.
- **`ph-node` gains CC, pitch-bend and per-note expression events** (the T2 contract gap). The Haus Synth's mod-wheel and bend become real events.

### Plugin hosting (DESIGN §6)

- **Formats:** CLAP and VST3 instruments and effects, in-process.
- **Scanner:** with a cache and a blocklist.
- **Plugin windows:** embedded in our floating plugin windows where the OS allows it, otherwise floating. A generic parameter UI is always available, and agents can drive any plugin by parameter id.
- **State:** saved with the project as separate files (DESIGN §10).
- **Crash handling:** a crash in a plugin call is caught as far as the platform allows, the node goes silent, and the plugin is marked *isolate* (out-of-process isolation itself is M4).
- **Test plugins:** the repo builds its own test plugins (a simple synth, a gain and a crash-on-demand plugin) so CI never depends on third-party plugins. Your own installed plugins are scanned locally to produce the compatibility report.

### Effects suite, M2 part (DESIGN §7)

Multiband compressor, gate/expander, convolution reverb (with a few generated impulse responses), chorus, flanger, phaser, bitcrush, stereo tools, and spectrum, loudness and phase analysers (as effect windows).

### Audio engine status (M2/T1)

- **Playback:** every playlist track with audio clips gets an audio-track node, summed into the master insert after the channels (there is no track-to-insert routing in the model yet). Its voices honour source offset, trim and slip, gain, sample-accurate fades with their curves, reverse, pitch and track mute. Seeks, loop wraps and plan swaps that rebuild a track restart its voices where playback lands; an unchanged track keeps its voices across a swap.
- **Stretch modes:** *Resample* and *Slice* interpolate (windowed sinc, `ph-dsp`) from source positions computed per output frame. *Stretch* runs Signalsmith Stretch in fixed 256-frame quanta anchored where the voice started (live: the cheaper preset; high-quality renders: the default preset; both with split computation). *Slice* places each transient (`ph_dsp::onset`, default sensitivity) on its beat and plays it unstretched, pitched by varispeed, with a 2 ms lead-in and a 2 ms declick where it is cut. Tempo-synced clips map song ticks to source frames, so they follow tempo changes; `tempo` automation clips now build the plan's tempo map.
- **Streaming:** sources of 10 s and longer stream from disk (WAV through `ph_formats::wav_stream`; other formats are decoded whole) in 8192-frame blocks into a per-track seqlock slot cache, filled about 1.4 s ahead by one prefetch thread per engine. The real device never waits (a missing block is silence and counts in `EngineStats.underruns`); the simulated device waits for the prefetch thread; offline renders read synchronously through the same slots.
- **Signalsmith route:** the thin binding (`crates/ph-stretch`): vendored headers, a C wrapper compiled by `cc`, hand-written externs. CI needs only a C++14 compiler, no libclang.
- **Oracle and real-time safety:** a song with pattern clips and audio clips in every mode (fades, reverse, pitch, a streamed source, a tempo ramp) renders bit-identically offline at blocks 64, 512 and 37 (serial and pooled) and on the simulated device, through plan swaps, a seek, a loop region crossing clips, mode changes and a stop. `assert_no_alloc` stress test with streaming clips and swaps; the C++ side counts its own allocations and stays at zero in the callback. A loom model covers the slot seqlock. Golden project `tests/projects/audio-clips`.

### Recording and MIDI status (M2/T8)

- **Recording path:** the audio thread reads each armed input once per chunk (a `cpal` input stream's ring on a device, `SimulatedInput` in tests), pushes the frames to record through an `rtrb` ring (3 s deep) to the `ph-record-writer` thread, which appends a 32-bit float WAV in `samples/` as they arrive and refreshes the header every second. The audio thread allocates and frees nothing: everything it retires (sources, finished captures, start packets) goes through a second ring to the writer thread. Takes are `Take N.wav`, never overwriting; a take that captured nothing leaves no file.
- **Monitoring** adds the input to the target's mixer insert (the channel's insert for a Sampler target, the master for a track) before its effects, through a feed buffer the insert node reads; with monitoring off the graph is untouched, so live stays bit-identical to offline, and offline renders never include it.
- **Latency compensation:** a take keeps its whole file and the clip plays from `source_offset = round-trip latency` (input device latency measured from the callback timestamps plus the queue, plus the output's measured buffering), so nothing is destroyed and the compensation can be redone. `record.start { latency_ms }` overrides the measurement. Only a loopback on the owner's interface can prove the figures.
- **Count-in and punch:** the transport is held while the metronome counts in; capture starts at the first frame after it. A punch range captures exactly its frames (chunks are not split) and then ends the take.
- **WASAPI exclusive mode:** not done. cpal 0.18 has no exclusive-mode switch for WASAPI (its only mention is mapping an exclusive-only error); `EngineConfig::exclusive` already says exclusive needs the `asio` build. A follow-up needs either cpal support or a small WASAPI binding of our own, for output and input together.
- **MIDI:** `midir` (MIT) behind `MidiBackend`; the router thread sends notes through the typing keyboard's preview path, and bend, wheel and pressure as `ph-node` events. Mapped controllers become `MidiEvent::Control` for the UI to apply as knob moves (so undo, agents and armed automation recording see ordinary edits). Mappings live in `<config>/midi-mappings.json`.
- **Known limits:** the input must run at the engine rate (no resampler); inputs are channel pairs; a mapping names a project object id, so it follows ids across projects; MIDI notes are placed at the position the audio thread last published (within a block); pressure has no listener in the built-in instruments; headless sessions apply no mapped controller (only the UI does).
- **Tests:** simulated inputs and a fake MIDI source only (`ph-engine` record and midi tests, `ph-commands` record_behaviour, `ph-control` record_tests, `ph-ui` midi_record), `assert_no_alloc` stress tests, a loom model of the take-done handoff, a Miri test. Owner checklist: [M2-recording-midi](../manual-tests/M2-recording-midi.md).

### Agent abilities status (M2/T9)

- **Tools:** `add_audio_clip`, `fit_to_tempo`, `add_automation`, `add_plugin_instrument`, `add_plugin_effect`, `propose` and `proposal_status` join the M1 set; every other M2 command is reachable through `run` and described by `describe_command`. `get_state` has views `audio`, `automation`, `plugins` and `proposals`; the musical diff reads audio, sample, automation, plugin and slicer edits in words.

- **Reference comparison:** `analyze { what: ["reference"], reference }` takes a registered sample id or an audio file in the folders agents may read. Tonal balance is per band after matching overall level (a quieter mix with the same balance reads as no difference); loudness is integrated, short-term max, range, true peak and crest; stereo is correlation and side-to-mid level. A few plain sentences say what to try. The reference is read, never copied; files longer than 15 minutes are cut.

Submit runs the batch on a copy and keeps the preview and a ghost; Accept re-runs it on the current project as one transaction attributed to the agent; Reject changes nothing. A proposal is stale when an object it changes was edited since (objects it creates are not compared: ids are never reused), when the project was replaced, or when it no longer applies. Agents read decisions with `proposal_status` or in a `proposal_decisions` block on their next reply. An agent cannot accept its own proposal. Transport, file, record, MIDI, UI and query commands cannot be proposed.
- **Known gaps:** ghosts are drawn for notes and playlist clips (a proposal that only changes the mixer or settings shows in the strip and its summary, not as a picture); proposals are not saved with the project; at most 8 pending proposals per author and 40 decided ones are kept; the audio excerpt is in the MCP and JSON-RPC content only. Owner checklist: [M2-agent](../manual-tests/M2-agent.md).

### Stretch quality (T1)

Measured by `cargo test -p ph-engine --lib stretch_quality -- --nocapture` on generated material (`ph-engine` test assets), through the real clip player: Stretch mode, tempo-synced 120 BPM material in projects at 84–156 BPM (time ratios 0.7–1.3).

- **Pitch error:** a 440 Hz sine and a 220 Hz tone with five harmonics, fundamental by autocorrelation over the middle half, worst of the two, in cents.
- **Pitch drift:** the same per 100 ms window over the steady 80%, max − min, in cents.
- **Level swing / error:** RMS of the sine per 50 ms window, max − min, and the mean against the original, in dB.
- **Onset error:** a click train (2 ms decaying noise bursts, one per beat): first 1 ms envelope frame within 20 dB of each click's peak, against its expected beat, worst, in ms.
- **Transient smear:** the extra time each click spends above −20 dB and above −40 dB of its peak, against the original click (6 ms and 10 ms), worst, in ms.

**Bounds (asserted by the test, both presets):** pitch error ≤ 1 cent, drift ≤ 2 cents, level swing ≤ 0.5 dB, level error ≤ 0.5 dB, onset error ≤ 3 ms, smear ≤ 5 ms at −20 dB and ≤ 25 ms at −40 dB.

**BPM detection** (`cargo test -p ph-analysis tempo -- --nocapture`): 40 generated drum parts at 62–195 BPM, four grooves (four on the floor, backbeat, syncopated breakbeat, half-time), 2–5 bars, with and without swing, half of them whole loops and half cut off-grid.

| groove | right tempo (within 1%) | half or double |
|---|---|---|
| four on the floor | 10/10 | 0 |
| backbeat | 10/10 | 0 |
| breakbeat | 5/10 | 5 |
| half-time | 2/10 | 8 |
| all | 27/40 | 13 |

No reading is off by more than an octave, and the worst error at the right octave is 0.42% (whole loops snap to exactly `60 × beats / seconds`). Breakbeats and half-time grooves read at half tempo above about 120 BPM: they are genuinely ambiguous, so `sample.detect_bpm` returns the double-tempo reading and its score in `alternatives`, and `sample.set_bpm` fixes it in one step.

**Performance** (`cargo xtask perf --report`, 48 kHz / 256 frames, the M1 reference project plus 8 tempo-synced stretched stereo clips at ratios 0.75–1.33, two of them streamed): measured 2026-10-13 on the local development machine (the perf baseline is named for a 7800X3D) while another agent was compiling, so the figures are noisy.

| | DSP load, mean | median | worst block |
|---|---|---|---|
| reference project, all cores | 12.4% | 9.4% | 241% |
| + 8 stretched clips, all cores | **12.9%** | **10.9%** | 107% |
| reference project, one thread | 65.4% | 61.4% | 137% |
| + 8 stretched clips, one thread | 81.3% | 74.3% | 303% |

Within the 25% target on all cores; a stretched stereo clip costs about 2% of one core (Signalsmith's cheaper preset with split computation). No underruns (the bench asserts `EngineStats.underruns == 0`; the simulated device waits for the prefetch thread, so this proves correctness, not disk speed). Worst blocks are mostly scheduling noise from the busy machine: the reference project alone shows the same kind.

**Loop-wrap spikes (fixed after the first measurement):** when the song looped back onto clips starting at the loop start, every Stretch voice warmed up in the same block (one output latency of stretcher work each): worst block 423% on all cores and 1318% on one thread, one-thread mean 111.5%. Stretch voices for the loop start are now pre-warmed during the last three output latencies before the loop end, at no more than about twice real time each, on a virtual timeline that makes the result independent of block size (live ≡ offline still bit-exact; a test checks that no 256-frame block computes more than 4 quanta per voice, against 18 for an unspread warm-up). After: 107% and 303% worst, one-thread mean 81.3%. Seeking into the middle of a stretched clip still warms its voice at once. The new metrics are reported by `cargo xtask perf` but not gated (no baseline yet).
