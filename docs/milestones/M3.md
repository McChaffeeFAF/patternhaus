# Milestone 3: Haus Sampler

Status: **started 2026-11-05.** The owner asked to begin work on the Haus Sampler. The plan implements DESIGN.md as decided: the §1 milestone line M3, §8 (Haus Sampler and library compatibility), and the parts of §4 and §9 that the sampler touches. The 96% weekly usage stop still applies.

**Defaults taken for the open decisions** (the owner may change any of them):
1. **Scripting and skins:** the Luau script host, the KSP compatibility interpreter and declarative instrument skins (DESIGN §8) move to a follow-on milestone, **M3b**. M3 ships the engine, the native format, the importers and a generic sampler UI. The M3 importers *read and keep* script text and UI data where a format has them, and report them as "not run yet", so nothing is lost.
2. **Plugin build:** Haus Sampler as a CLAP/VST3 plugin for other DAWs is postponed to M4, alongside sandboxed plugins.
3. **Kontakt corpus:** the owner's unencrypted libraries are read in place, read-only, from a folder the owner names when the check runs. Nothing from them is committed. The report (`docs/parity/kontakt-corpus.md`) lists library names and results only.
4. **SF3** (Ogg-compressed SoundFont) is in scope, because `ph-formats` already decodes Ogg.
5. **Releases** stay as in M2. No tag without the owner's OK.

**Sections (phases):**
- **A:** T0 contracts ‖ T1 format specs (clean room).
- **B:** T2 sampler engine ‖ T3 native format and SFZ.
- **C:** T4 SF2/SF3, DecentSampler and EXS ‖ T5 sampler UI.
- **D:** T6 Kontakt import ‖ T7 agent features.
- **E:** T8 integration, QA and tag.

At most two local agents run at a time.

## Goal

A person in the UI, or an agent through MCP alone, can load a **real multi-sample instrument** (a sampled piano, a drum kit with round robins, an orchestral patch with articulations) from the formats people already own and play it in a song:
- open SFZ, SF2/SF3, DecentSampler, EXS24 and **unencrypted** Kontakt instruments, with a plain report of anything approximated or skipped;
- play big libraries straight from disk, without loading gigabytes into memory;
- see and edit the zone map: key and velocity ranges, round robins, groups, keyswitches;
- save the result in Patternhaus's own open instrument format.

**Hard boundary (DESIGN §8):** no circumvention of encrypted or licence-locked libraries (NI "Player" libraries, Native Access–activated content). The sampler detects them and says so plainly. It never tries to decrypt them.

## Acceptance criteria

M3 is done when all of these hold on `main` with CI green on Windows, Linux and macOS:

1. **Agent acceptance test (MCP only).** A scripted agent:
   - loads a generated multi-sample instrument from SFZ (velocity layers, round robins, release triggers, two keyswitched articulations) and a generated SF2 drum kit;
   - writes a 16-bar part that uses both articulations;
   - inspects the zone map through `get_state` and edits it (moves a zone, changes a velocity split);
   - saves the instrument in the native format, reopens the project and renders it.

   The export matches the offline oracle, and `analyze` finds the intended key and chords.
2. **Format conformance.** Every importer has generated fixtures that cover its supported opcodes or chunks. Each fixture renders to a reference, and an import, save-as-native and reopen round trip renders identically. Every importer is fuzzed in CI. Each format has a per-feature parity table in `docs/parity/haus-sampler.md`, marked supported, approximated or skipped.
3. **Kontakt corpus (owner).** Over the owner's local libraries, the report lists every instrument as opened, refused as encrypted, or failed with a reason. At least 90% of the unencrypted instruments in scope (Kontakt 1.5–7: zones, loops, NCW, monoliths) load with the right zone count, key and velocity ranges, root keys and loop points. That is checked against an independent reading of each file's metadata. Encrypted content is reported as such and never decrypted.
4. **Streaming.** A generated library of about 2 GB plays a 128-voice stress pattern at 48 kHz with 256-sample buffers. It never underruns. Resident memory stays within the preload budget plus a fixed margin. Loading the instrument takes under 2 seconds on the development machine, because only the preload is read.
5. **Oracle and real-time safety, extended.** The sampler's live output is bit-identical to the offline render, including round-robin and random choices (seeded per render), release triggers, legato and streamed playback. The audio thread doesn't allocate under `assert_no_alloc`, including voice stealing and stream starvation.
6. **Performance.** The reference project plus a 64-voice streamed piano part stays within 30% DSP load on the reference machine.
7. **By hand (owner).** Load one of your own SFZ or Kontakt libraries, play it from your MIDI keyboard, switch articulations, edit a zone in the UI, save the project and reopen it.
8. **Coverage and parity.** Every new command has schema and behaviour tests. Every M3 row of `docs/parity/fl-studio.md` and `docs/parity/haus-sampler.md` has both columns filled.

## Scope

### Engine (T2): `ph-sampler`
- **Zones:** key range, velocity range, root key, tune, volume, pan, sample start/end, loop (forward, ping-pong, release-loop), crossfade loops, reverse.
- **Groups:** shared settings, per-group amp and filter envelopes, LFOs, filter, and voice limits with stealing.
- **Triggers:** attack and release triggers (release with decay over time held), round robins (sequential and random, seeded), keyswitches, CC-switched articulations, legato and portamento for mono groups.
- **Crossfades:** velocity crossfades and CC crossfades (dynamics on the mod wheel).
- **Modulation matrix:** sources (velocity, key, CC, pitch bend, aftertouch, LFO, envelope, random-per-note) to targets (pitch, volume, pan, cutoff, resonance, sample start). Depth and curve.
- **Streaming:** reuse the M2 disk streamer (`ph-engine` prefetch) with a per-sample preload. Voices start from the preload while the stream fills.
- **Multi-out:** zone groups can feed separate outputs on the instrument node (DESIGN: true multi-out).
- **Per-group effects:** an insert chain per group, made of built-in effects.
- The M1 `ph.sampler` stays as the simple one-shot instrument. Haus Sampler is a new instrument, `ph.haus_sampler`.

### Native format (T3)
- A folder: `instrument.toml`, `samples/`, optional `ui/` and `scripts/` (empty until M3b). Open, documented in `docs/formats/haus-instrument.md`, versioned with migrations.
- Projects reference instruments by path or embed a copy (the owner's "collect into project" choice per instrument).

### Importers: `ph-sampler-formats`
In DESIGN's priority order:
1. **SFZ** (T3): headers `<control> <global> <master> <group> <region> <curve> <effect>`, `#define`/`#include`, the v1 opcodes and the common ARIA/v2 ones. Unknown opcodes are listed, never silently dropped.
2. **SF2/SF3** (T4): presets, instruments, generators, modulators, sample links.
3. **DecentSampler `.dspreset`** (T4): groups, samples, effects, simple UI controls read as data.
4. **EXS24 `.exs`** (T4).
5. **Kontakt `.nki` / `.nkm` / `.ncw` / monoliths** (T6): unencrypted only. Zones, loops, NCW decode and monolith extraction first. Then groups, envelopes and filters as far as the spec covers them. Encrypted files are detected and refused with a plain message.

### UI (T5)
- A sampler window in the FL style (separate window, DESIGN §9): a zone map (keys × velocity, drag to move or resize, colour by group), a group list, a zone inspector, an articulation and keyswitch strip on the keyboard, and a modulation matrix table.
- A generic panel for every instrument (no skins until M3b).
- Drop a folder of samples, or any supported file, onto the channel rack to create an instrument (auto-map by note names in file names, with a preview).

### Agent features (T7)
- `sampler.*` commands: load, import, zone add/move/set, group set, keyswitch set, modulation set, save as native, report.
- `get_state { view: zones }` returns a compact zone map, and `snapshot` gets a zone-map image.
- The import report is readable over MCP.

## Clean-room rule for formats

The same rule as FLP in M2 (T4/T5):
- **T1 writes the specs** in `docs/formats/` in its own words. Sources: public specifications (SFZ, SoundFont 2.04), public documentation and articles, and analysis of files the project generates itself or that are freely redistributable. Open-source converters (e.g. ConvertWithMoss, LGPL-3.0) may be consulted for **facts** about a format. Their code is never copied or translated, and each spec cites its sources.
- **Implementers (T3, T4, T6) work from our specs only.**
- No disassembly or decompilation of Kontakt, Logic or any other binary. No NI or Apple code, samples or presets in the repo.
- Encrypted content is out of scope, permanently.
