## Goal

A person in the UI, or an agent through MCP alone, can:
- start a project, load drums and a synth, and program steps and piano-roll notes;
- mix with built-in effects and arrange patterns in the playlist;
- hear it play live without glitches, save it, reopen it, and export a WAV/FLAC.

## Acceptance criteria

M1 is done when all of these hold on `main` with CI green on Windows, Linux and macOS:

1. **Agent acceptance test (DESIGN §12).** A scripted agent builds the beat through MCP only:
   - sets 4 channels (kick, snare, hat on samplers; bass on Haus Synth);
   - programs the patterns and arranges 8 bars in the playlist;
   - puts EQ and compression on an insert and reverb on a send;
   - exports a WAV.

   The render must match the offline oracle, measure between -16 and -8 LUFS, and have no clipping. The test also checks that the agent received an image and an analysis report.
2. **The same story by hand.** The owner does the same in the UI using FL-compatible shortcuts. The result plays live at a 256-sample buffer with zero dropouts over 5 minutes.
3. **Co-editing.** A human and an agent edit at the same time:
   - per-author undo reverts only the agent's work;
   - a conflicting undo stops and reports the conflict.
4. **Save and reopen.** The project round-trips as a readable `project.json` folder, byte-stable when saved twice.
5. **Real-time safety.** No allocation or locking on the audio thread under `assert_no_alloc`. That includes a stress test of continuous edits during playback.
6. **Oracle.** Real-time render through a simulated device is bit-identical to offline render on the golden projects.
7. **Performance.** On the owner's machine (Ryzen 7 7800X3D), the reference project plays at 48 kHz with a 256-sample buffer at no more than 25% engine DSP load (engine CPU meter: time spent processing ÷ buffer duration). The reference project has 16 channels, 8-voice synth chords and 8 insert effects. Its numbers become the CI performance baseline.
8. **Coverage.** Every registered command has a schema test and a golden test.
9. **Parity tracker.** `docs/parity/fl-studio.md` lists every M1 feature with both its *wired* and *behaves* columns filled in.

## In and out of M1

**In:**
- **Model:** ph-core model, patches, command registry, per-author history, transactions, co-editing queue.
- **Engine:** general node graph, multicore scheduler, offline render, real-time via cpal (WASAPI/CoreAudio/ALSA), plan swap, per-node CPU meter, basic overload shedding, adaptive buffer notice, FTZ/DAZ.
- **Instruments:** Sampler (one-shot and loop); Haus Synth (full spec from §7).
- **Effects:** EQ, compressor with sidechain, limiter, reverb, delay, filter, saturation.
- **Agent interface:** JSON-RPC, MCP, CLI; scopes; events; analysis (LUFS, peak, spectrum, onsets, key and chords, clash warnings, mix health); images (spectrogram, waveform, piano roll, playlist).
- **UI:** egui with an FL-style floating workspace (DESIGN §9, revised 2026-10-10): docked browser; floating channel rack and step sequencer, piano roll, playlist, mixer, transport, history panel. FL-compatible keymap, dark and light themes.
- **Formats:** project folder with v1 schema and migrations scaffold; WAV/AIFF/FLAC/MP3/OGG sample import; WAV and FLAC export; MIDI file import and export.
- **Factory content:** a generated drum kit (`tools/soundgen`) plus Haus Synth presets, with provenance recorded.
- **Repo infrastructure:** CI, layering check, provenance check, AGENTS.md, parity tracker.

**Deferred** (scheduling calls Claude made within the decided design):
- Agent **preview mode** moves to M2. It's an optional mode, and it needs the patch rebase machinery to be proven first.
- **MIDI controller input** stays in M2, as decided. Typing-keyboard-to-piano input is in M1, since it's cheap and FL users expect it.
- Anticipative processing ships in M4, but **M1 must still mark every render-plan node live or anticipative** (DESIGN §4).

## Contracts fixed in T0

Every parallel track builds against these, so they must not change without Claude's review:

1. **`ph-core`:** the `Project` model (the provisional sketch, revised) plus `ObjectPath`, `Patch { path, before, after }` and `PatchSet`.
   - Model mutations go only through functions that return patches.
   - `apply(&mut Project, &PatchSet)` and `invert(&PatchSet)` live here, so undo and the planned preview mode share one mechanism.
2. **`ph-commands`:** the command trait and registry.
   ```rust
   CommandSpec { id, summary, scope: Scope, mutating, params_schema }
   fn run(ctx: &mut CommandCtx, params: serde_json::Value) -> Result<CommandOutput>
   CommandOutput { result: Value, patches: PatchSet, summary: Option<String> }
   CommandCtx { project: &Project, author: Author, host: &mut dyn Host }
   ```
   - `Host` is the side-effect port to the engine and filesystem: transport, render, file I/O.
   - The `Session` owns the queue, history, transactions and per-author undo.
3. **`ph-node`:** the internal plugin interface for every built-in instrument and effect, mirroring CLAP's concepts so wrapping them as CLAP/VST3 later is mechanical.
   ```rust
   trait Processor: Send {
       fn descriptor(&self) -> &NodeDescriptor;   // ports, params (id, name, range, default, unit)
       fn activate(&mut self, sample_rate: f64, max_block: usize, quality: Quality);
       fn process(&mut self, ctx: &ProcessContext, io: &mut ProcessIo) -> ProcessStatus;
       fn set_param(&mut self, id: ParamId, value: f64);   // real-time safe
       fn reset(&mut self);
       fn save_state(&self) -> Vec<u8>;
       fn load_state(&mut self, state: &[u8]);
   }
   ```
   - `ProcessIo` carries audio buffers and a sorted, sample-stamped event list (notes, param changes).
   - `process` is called only on the audio thread and must not allocate.
4. **`ph-engine` API:**
   - `Engine::start(device_config)`, `engine.set_project(Arc<Project>)`;
   - `engine.transport(cmd)`;
   - `render_offline(&Project, range, RenderSettings) -> AudioBuffer`;
   - `engine.stats()` for CPU and overloads;
   - the engine implements the transport and render half of `Host`.
5. **Repo rules:**
   - **AGENTS.md:** layering, real-time rules, how to add a command or node, test expectations, clean-room policy, commit sign-off.
   - **CI:** `cargo xtask check-layers`, fmt, clippy `-D warnings`, tests on all 3 OSes, and the provenance check.

## Risks

| Risk | Mitigation |
|---|---|
| The UI (T5) is the largest track and egui docking is unproven at DAW scale | Start the piano roll widget first, as a spike inside T5, and measure frame time on 10k notes before building other panels |
| Per-author undo is subtle (conflicts, transactions) | T1 builds it test-first with a property test: random interleaved edits by two authors, undo one author, check the other's state is untouched |
| Real-time bugs show up only under load | `assert_no_alloc` from day one, the stress test in T3 rather than waiting for T7, and the oracle test in T3 |
| Key and chord estimation quality | A known-answer test set built from generated MIDI renders (we know the true chords) |
| Cross-platform audio quirks | M1 must *pass CI* on Linux and macOS, but live-audio sign-off happens only on Windows (the owner's machine) |
| Contract churn breaking parallel tracks | T0 contracts change only through Claude, with a version note in AGENTS.md |
